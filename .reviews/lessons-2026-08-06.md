# Lessons — storage hardening + readiness pass (2026-08-06)

Failure patterns worth not repeating. Written for the next session, not as a diary.

---

## 1. I overstate what the code guarantees — repeatedly

Three separate times, the *prose* was wrong while the code was fine or fixable:

| Claim | Reality |
|---|---|
| §10.4 table: "변경 잠금" | `storageLocked` gates persistence effects only. Edit/delete/grade handlers stay live. |
| `afe4186`: "recorded only after the file leaves" | `downloadJSON` is `<a>.click()` — fire-and-forget, no completion signal. |
| Duel: 3 of my 4 review findings | Downgraded to PARTIAL. I asserted reach I had not verified. |

In a project whose stated principle is *"추측해서 데이터를 만들지 않는다"*, documentation
that overstates a guarantee is the same defect class as data that lies.

**Rule:** before writing "only after X" / "locked" / "guaranteed", find the line that
enforces it. If you cannot point at it, weaken the sentence.

## 2. Local green ≠ CI green, for structural reasons

The same class-collision bug shipped **twice**, passing locally and failing in CI both times.

Cause: `navigator.storage.persisted()` returns **true** on the local Chromium profile
(origin has engagement history) and **false** in CI. So the eviction warning renders only
in CI, and a bare `.io-error` locator in a pre-existing test then matches two elements —
Playwright strict-mode violation.

**Rule:** environment-dependent browser APIs (`storage.persisted`, permissions, quota,
`prefers-*`) make local runs a weaker signal than CI. Do not treat a local pass as
verification for anything touching them. This is the concrete argument for the PR CI
added in `8c7dba6` — it catches what local runs structurally cannot.

## 3. Shared CSS classes + bare test locators = landmines

`.io-error` was the hook for import/export errors. I reused it for two new Settings
messages. Any pre-existing test asserting on a bare `.io-error` then breaks the moment a
second one renders.

**Rule:** a new message with a different *meaning* gets its own class, even when it looks
identical (`.backup-stale`, `.storage-warn` both just `color: var(--error)`).
Latent instance still present: `tests/storage-failure.spec.js:384` asserts on a bare
`.io-error` inside the record sheet — safe only because `photo.error` is currently the
sole one rendered there.

## 4. Adding a gate flag without backfilling silently disables the feature

`hasUserData()` gates the backup reminder. Existing users' notes predate the flag, so the
reminder was **off for exactly the people with the most to lose**. Caught by Codex
stop-review, not by any test — every test starts from `freshApp`.

**Rule:** any new "has the user done X yet" flag needs a backfill path *and* a test that
starts from pre-flag state. Do not rely on a suite whose fixtures all begin clean.

Corollary discovered while fixing it: **"stored notes exist" cannot distinguish a returning
user from a fresh install**, because the first boot seeds and persists. Distinguishing them
requires recording the answer at seed time, not inferring it later.

## 5. Measure before prioritising

I spent most of the session on quota-exhaustion paths (D-gc, E). Then measured: a heavy
note is ~1.3KB, so 2,000 notes = 2.4MB against a 5–10MB limit. **Quota is not a realistic
threat for this user.** Meanwhile `navigator.storage.persist` was called nowhere, leaving
the origin evictable — the actually-likely way the data dies.

**Rule:** for a single-user app, cheap measurement reorders the backlog more than more
review does. Ask "what is the most likely way this data is lost?" before "what is the most
severe bug I can find?"

## Process notes that worked
